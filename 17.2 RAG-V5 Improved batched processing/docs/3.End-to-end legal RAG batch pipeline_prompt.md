## Goal (one line)

Refactor and extend RAG V5 to use a new Postgres DB (`legalrag_v5_db`), switch from single-row DB writes to file-backed batching (flat files + pickle), centralize DB logic, ensure safe transactions/rollback, add lightweight LegalBERT grammar corrections during OCR (with logging), and make all parameters configurable via `.env`.

---

## High-level constraints (must-follow)

1. **Do not change code flow.** Only modify code where necessary to achieve the goals.
2. **Make minimal, testable changes.** Implement step-by-step; each step must have tests and verification.
3. **All configuration via `.env`.** No hard-coded paths or DB names.
4. **No per-row DB writes.** Save outputs, examples, chunks and embeddings to local files (flat text/csv/json and pickles). Then load files and write to Postgres in batch (single or multiple batches).
5. **Centralized DB module.** SQL statements should be consolidated into a single DB access layer/module.
6. **Safe transactions.** If a DB transaction fails, automatically `ROLLBACK` without manual intervention.
7. **OCR corrections using LegalBERT.** Do simple grammar/typo correction during OCR extraction, log every correction (original → corrected) to an audit log.
8. **Chunking reads from folders.** Chunking should read files present in the chunking source folder — do not consult DB to decide what to chunk. After successful chunking, delete the source file.
9. **Step gating.** Implement step-by-step migration; do not proceed until each step has passed its tests.
10. **No fallback logic.** Do not any fallback code. Log all errors instead.

## File-based batching format

- **Chunks / embeddings / examples / outputs** should be saved first to files under `BATCH_FILE_DIR` (or `STORAGE_DIR`) in well-known formats:

  - `chunks-<timestamp>-part<N>.jsonl` — newline-delimited JSON for chunk metadata & text.
  - `embeddings-<timestamp>-part<N>.pkl` — pickled list/array of embeddings (numpy arrays or lists).
  - `examples-<timestamp>-part<N>.jsonl`
  - `outputs-<timestamp>-part<N>.jsonl`

- **Naming convention** must include timestamp and part number to avoid collisions.
- Each JSONL line should include document id, chunk id, text, metadata, created_at, source_filename.
- **Pickle usage**: use `pickle.HIGHEST_PROTOCOL`. If embeddings are numpy arrays, store as list or use `numpy.save` paired with JSONL metadata.
- **Atomic write**: write to a temp file then `os.replace()` to final filename.

## Database centralization

Create a single DB module, e.g. `db/pg_client.py` (or `db/__init__.py`) that exposes:

- `get_pool()` / `get_conn()` — connection pool factory using config from `.env`
- `execute(query, params=None)` — for single statements
- `execute_batch(query, records)` — batch insert helper
- `transaction()` — context manager for transactions; ensures commit on success and rollback on exceptions
- `migrate_schema_if_needed()` — optional schema creation (idempotent)
- All SQL queries (DDL/DML) live in `db/sql.py` as well-defined constants or functions (no inline SQL scattered elsewhere)
- Provide typed/clear methods: `insert_chunks_batch(items)`, `insert_embeddings_batch(items)`, `insert_examples_batch(items)`, `upsert_doc_status(doc_id, status)` etc.

**Safety**: All DB writes must occur inside `transaction()` context manager. If any exception occurs, auto-rollback.

---

## Transaction behavior (implementation detail)

Use a context manager pattern:

```python
with db.transaction() as tx:
    tx.execute_batch(insert_chunks_sql, chunk_records)
    tx.execute_batch(insert_embeddings_sql, embedding_records)
    # If any of the above fails, rollback is automatic and exception propagates
```

Ensure:

- Proper exception handling (log errors).
- Retries on transient errors (optional, configurable via `.env`: `DB_MAX_RETRIES`, `DB_RETRY_DELAY_MS`).

## OCR extraction + LegalBERT corrections

During OCR extraction:

1. Extract raw text as before.
2. Run a lightweight correction pass using LegalBERT (or a fine-tuned spell/grammer-correction wrapper around the model). Correction rules:

   - Only correct obvious token-level mistakes (typos, wrong letters) and simple word splits/merges. Avoid changing meaning.
   - Example corrections to detect and fix:

     - `"Folitical farties" -> "Political parties"`
     - `"evelopment" -> "development"`

   - For ambiguous corrections, **do not automatically change** — instead leave a suggested correction (but by default, apply only high-confidence corrections).

3. Log **each** correction line to `AUDIT_CORRECTIONS_FILE` as JSONL:

```json
{
  "timestamp": "2025-11-23T15:12:34Z",
  "source_file": "contract-123.pdf",
  "location": { "page": 3, "offset": 432 },
  "original": "Folitical farties",
  "corrected": "Political parties",
  "confidence": 0.98,
  "rule": "legalbert_spellfix_v1"
}
```

4. Save both the corrected text (for downstream chunking) and the original raw text metadata (so you can audit later).

**Implementation hints**:

- Use model only for short spans (sentence-level) to limit cost and latency.
- Provide `LEGALBERT_CONFIDENCE_THRESHOLD` in `.env` to control when automatic correction is applied.
- Provide a `--dry-run` or `OCR_AUDIT_ONLY` flag for first runs that just logs suggested corrections without applying them.

## Chunking workflow (folder-driven)

- Input folder: `SOURCE_DIR` (configured via `.env`).
- **Rule**: If a file exists in `SOURCE_DIR`, it **needs** chunking.
- Chunking logic:

  1. Read file from `SOURCE_DIR`.
  2. Extract text (OCR if needed), apply LegalBERT corrections.
  3. Create chunks and their metadata; save chunk JSONL and embeddings to `BATCH_FILE_DIR` (or `STORAGE_DIR`) as described above.
  4. Only after files are fully written and validated, delete the source file from `SOURCE_DIR`.

- **No DB checks** to decide on chunking. DB may be used only after chunk files are created for batch ingestion.

---

## Batch-to-DB ingestion

- A separate ingestion module reads `BATCH_FILE_DIR` for ready batch files.
- For each pair (chunks JSONL + embeddings pickle) perform:

  - Validate file integrity (line counts match, schema valid).
  - Use `db.transaction()` and `insert_*_batch` methods to write in batches of `BATCH_SIZE`.
  - Remove or archive batch files only after successful DB commit.
  - If the transaction fails: the transaction should rollback and the batch files remain for retry.

- Support parallel ingestion (configurable `BATCH_WRITE_PARALLEL`) but keep each batch insert in a single DB transaction to maintain consistency.
